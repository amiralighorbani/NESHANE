# ✦ نشانه — پلتفرم فال و تست شخصیت (MVP)

پلتفرم فال با **FastAPI + Jinja2 (SSR خالص)** و فرانت‌اند دست‌ساز (HTML/CSS/JS بدون هیچ کتابخانه یا فریم‌ورک).
کاربر با شمارهٔ موبایل و کد یک‌بارمصرف **ثبت‌نام** می‌کند، همان‌جا نام کاربری و رمز عبور می‌سازد و
از آن به بعد فقط با همان دو مورد **وارد** می‌شود؛ اطلاعات تولدش را می‌دهد، نیت و موضوع فالش را
می‌گوید و یک **خوانش کامل** می‌گیرد: فال حافظ با تعبیر، کارت تاروت، طالع‌بینی، انرژی روز در پنج حوزه،
اقلام شانس، کارهای امروز/امروز-نه، نمودار انرژی و یک جملهٔ پایانی.

> این پروژه یک پروتوتایپ است. محتوا برای سرگرمی و خودشناسی است، نه پیش‌گویی یا جای مشاورهٔ تخصصی.

## اجرا

```bash
python -m pip install -r requirements.txt
cp .env.example .env        # و بعد مقادیرش را پر کن (ویندوز: copy)
python -m uvicorn app.main:app --reload --port 8020
```

سپس <http://127.0.0.1:8020> را باز کنید. خودِ `app/main.py` هم پورت ۸۰۲۰ را پیش‌فرض دارد
(`python -m app.main`).

- `python -m pip install -r requirements.txt` — وابستگی‌ها: FastAPI، Uvicorn، Jinja2، python-multipart، Pydantic
- هیچ مرحلهٔ build، هیچ `node_modules`: فایل‌های CSS/JS مستقیم سرو می‌شوند
- دیتابیس و لاگ‌ها در `data/` است (به git نمی‌رود)

### کلیدها و رمزها (مهم)

هیچ کلید یا رمزی در سورس پروژه نیست. همه در `.env` (که در `.gitignore` است) یا در متغیرهای
محیطی سرور می‌مانند. `app/env.py` در اولین `import` این فایل را می‌خواند و **متغیرهای واقعی
محیط همیشه بر `.env` اولویت دارند**. اگر کلید مدل زبانی نگذاری، اپ بدون هیچ خطایی با متن‌های
پایه کار می‌کند. نمونهٔ کامل در `.env.example` است.

## جریان کار گیت

```
develop  ← تمام تغییرات روزمره (شاخهٔ پیش‌فرضِ کار)
main     ← فقط نسخه‌های ریلیز؛ تگ نسخه روی همین شاخه
```

هر تغییر یک کامیت معنادار روی `develop` است (نه کامیت‌های بزرگ و مبهم):

```bash
git switch develop                     # همیشه روی develop کار کن
git add <files> && git commit -m "type: چرا این تغییر"
git push origin develop
```

برای ریلیز، `develop` روی `main` مرج و همان‌جا تگ می‌شود:

```bash
git switch main && git merge --no-ff develop
git tag -a v1.1.0 -m "نشانه ۱٫۱٫۰"
git switch develop && git push origin main --follow-tags
```

نسخهٔ جاری در `app/__init__.py` (`__version__`) و در تگ‌ها (`v1.0.0`) هم‌تراز نگه داشته می‌شود.

## پنل مدیریت (روت مخفی)

پنل روی یک مسیر تصادفی است و **هیچ‌جای سایت به آن لینک نشده**. مسیر مخفی، نام کاربری و رمز
همه در `.env` می‌مانند؛ **هیچ رمز و مسیر مخفی‌ای در سورس پروژه نیست**:

```ini
NESHANE_ADMIN_PATH=/یک-مسیر-تصادفی/
NESHANE_ADMIN_USER=نام-کاربری-تو
NESHANE_ADMIN_PASSWORD=رمز-تو
```

با این تنظیمات، آدرس ورود می‌شود `http://127.0.0.1:8020/یک-مسیر-تصادفی/`.

رمز به‌صورت متن ساده در کد نیست؛ در حافظه با PBKDF2-SHA256 (۲۶۰٬۰۰۰ تکرار) هش می‌شود و
مقایسه با `hmac.compare_digest` انجام می‌شود. اگر نمی‌خواهی رمز حتی در `.env` هم متن ساده
باشد، فقط هشش را بگذار:

```bash
python -c "from app import admin_auth; print(admin_auth.make_hash('رمز-تو'))"
# → NESHANE_ADMIN_PASSWORD_HASH=<هش>   و   NESHANE_ADMIN_PASSWORD_SALT=<نمک>
```

اگر هیچ رمزی تنظیم نشده باشد، ورود به پنل **بسته** می‌ماند و صفحهٔ ورود خودش دلیل را می‌گوید؛
هیچ رمز پیش‌فرضی وجود ندارد که کسی بتواند حدس بزند. پنج تلاش ناموفق، ورود را ۱۵ دقیقه قفل
می‌کند و همهٔ ورودها/خطاها در صفحهٔ «رویدادها» ثبت می‌شوند.

امکانات پنل:

- **داشبورد:** کاربران (کل، ۲۴ ساعت، یک هفته)، خوانش‌ها به تفکیک روش، تست‌های تمام‌شده، ورودهای مدیر
- **کاربران:** جست‌وجو در نام، نام خانوادگی، شماره، **نام کاربری** یا شهر، صفحه‌بندی و دکمهٔ «پرونده»
- **پروندهٔ کاربر:** همهٔ چیزی که کاربر وارد کرده — نام و نام خانوادگی، جنسیت، تولد شمسی، ساعت تولد،
  شهر، سن تقریبی، خلاصهٔ «زندگی در عدد»، پیش‌نویس سفر (روش، موضوع، **متن نیت**) — به‌همراه همهٔ
  فال‌هایش و **همهٔ تلاش‌های تست شخصیت با متن هر سوال و گزینهٔ انتخاب‌شده**، امتیازها، نتیجهٔ نهایی
  و رویدادهای همان کاربر
- **پروندهٔ کامل کاربر** (`users/{id}/dossier`): همان داده‌ها در یک گزارش تمیز و آمادهٔ چاپ/PDF —
  هویت و نیت، هر ۳۰ کارت «زندگی در عدد»، همهٔ آزمون‌ها با تک‌تک سوال‌ها و جواب‌ها، همهٔ فال‌ها با
  ابیات تعبیر و راهنما. دکمهٔ «چاپ / PDF» و خروجی `users/{id}/dossier.csv` هم دارد؛ برای فرستادن
  دادهٔ یک کاربر به خودش ساخته شده.
- **مدیریت:** ویرایش پروفایل، پاک‌کردن پیش‌نویس سفر، **ساخت فال برای کاربر** و دیدن لینکش،
  حذف خوانش و حذف کامل کاربر (با تأیید متنی)
- **استخر فال (CRUD کامل):** ساخت کارت تازه، ویرایش متن/ابیات/تعبیر/راهنما/مضمون، ویرایش روی کارت
  آماده و **بازگرداندن به متن اصلی پروژه**، حذف کارت ساختهٔ مدیر، و **پنهان‌کردن/بازگرداندن** کارت
  آماده. فیلتر بر پایهٔ منبع، مضمون و وضعیت + جست‌وجو. تغییرات در جدول `fortunes` ذخیره می‌شوند و
  بی‌درنگ روی فال کاربران اثر می‌گذارند.
- **خوانش‌ها:** فهرست همهٔ خوانش‌ها با فیلتر روش + نمایش کامل یک خوانش (شامل JSON خام)
- **خروجی CSV:** `users.csv`، `readings.csv`، `attempts.csv` (سوال و جواب کنار هم)، `events.csv`

دسترسی بدون نشست، به صفحهٔ ورود پنل هدایت می‌شود و کوکی نشست پنل `HttpOnly`، `SameSite=Lax`
و محدود به همان مسیر مخفی است. درخواست POST از دامنهٔ دیگر هم رد می‌شود.

## فال‌های آماده (۱۱۷ کارت)

| استخر | تعداد | توضیح |
| --- | --- | --- |
| غزل‌های واقعی از نت | ۱۰۰ | ابیات واقعی دیوان حافظ (مطلع + مقطع)، تعبیر ساخته‌شده با موتور تم |
| کارت‌های دست‌نویس پروژه | ۱۷ | تعبیر و راهنمای نوشته‌شده توسط خود پروژه |

هر خوانش با مولد قابل‌تکرار (`random.Random`) یک کارت تصادفی از این استخر می‌گیرد؛ پس
همان اطلاعات + همان روز = همان فال، و «فال تازه» با نمکِ نو، کارت نو می‌دهد.

**منبع ابیات:** دیتاست JSON دیوان حافظ از مخزن `arsamadineh/Persian-Quote-API` (مجوز MIT).
متن دیوان حافظ مالکیت عمومی است. **تعبیرها از نت گرفته نشده‌اند**؛ هیچ متن شخص ثالثی در پروژه کپی نشده.

### ساخت دوبارهٔ استخر

```bash
python tools/build_fortunes.py
```

این اسکریپت غزل‌ها را می‌گیرد (اول از `data/_hafez_verses.json` و اگر نبود از نت)، ۱۰۰ غزل
یکنواخت در سراسر دیوان انتخاب می‌کند، تم هرکدام را با موتور تم تشخیص می‌دهد و
`app/content/ghazals.py` را می‌نویسد. برای افزودن غزل بیشتر، `WANTED` در همان فایل را بالا ببر.

موتور تم (`app/content/fortune_themes.py`) ده مضمون دارد (عشق، رندی، غم، امید، گذر زمان، ریا،
نیاز، خرد، راز، توبه) و از هر غزل، مضمون را با تطبیق **واژه‌ای** (نه زیررشته‌ای) تشخیص می‌دهد و
تعبیر را از قالب‌های آغاز/بدنه/پایان می‌سازد؛ به همین دلیل با ۱۰۰ غزل، متن تعبیرها تکراری نمی‌شود.

## پیام‌های کوتاه (توست) و مدیریت خطا

هر پیام کوتاه برنامه — نتیجهٔ ثبت‌نام، خطای فرم، هشدار لبه‌ها — به‌شکل یک **توستِ
انیمیشنی** از پایین صفحه سر می‌رسد و خودش می‌رود. این یکدستی از سه‌جا می‌آید:

- **`app/flash.py`** پیام را در یک کوکی کوچک می‌گذارد، پس از ریدایرکت‌های
  «POST → Redirect → GET» هم گم نمی‌شود؛ صفحهٔ بعدی آن را می‌خواند و کوکی پاک می‌شود
  (پس با رفرش تکرار نمی‌شود).
- **`templating.render`** تنها راه رندر صفحات است و خطاهای صفحه را خودکار به توست
  تبدیل می‌کند. یعنی هر فرمی در کل برنامه — قدیم و جدید — از همان لحظه انیمیشن دارد.
- **`app/static/js/app.js`** تابع `toast(...)` را می‌سازد: چهار حالت (موفق، خطا، هشدار،
  اطلاع)، نوار زمان، مکث با نگه‌داشتن، بستن با کشیدن انگشت، و `prefers-reduced-motion`.
  برای کارهای تازه: `toast("متن", "success")` یا `toast("متن", {kind: "error", title: "…"})`.

### هیچ ورودی‌ای سرور را نمی‌ترکاند

مسیرهای خصوصی محافظت دارند و **دلیلش را هم می‌گویند** (قبلاً کاربر بی‌توضیح به صفحهٔ ورود
پرت می‌شد):

- **تضاد داده:** بین «چک‌کردن آزاد بودن نام کاربری» و «نوشتن در دیتابیس» فاصلهٔ زمانی هست.
  اگر دو نفر هم‌زمان یک نام را بزنند — یا کاربر روی موبایل دکمه را دو بار بزند — قید یکتایی
  دیتابیس فعال می‌شود. حالا این حالت یا بی‌خطر رد می‌شود یا پیام روشن می‌گیرد، **نه خطای ۵۰۰**.
- **مالکیت فال و تست:** توکنِ لو‌رفتهٔ فال برای کاربر دیگری باز نمی‌شود و شناسهٔ تلاشِ تست
  (که در آدرس می‌آید) چک می‌شود تا جواب کاربر داخل تلاش کس دیگری ننشیند.
- **خطاهای استاندارد:** ۴۰۴، ۴۰۵، ۵۰۳ و خطای پیش‌بینی‌نشده هر کدام یک صفحهٔ برند‌دار با توست
  می‌گیرند؛ Traceback فقط در لاگ سرور می‌ماند. درخواست‌های JS (`Accept: application/json`)
  پاسخ JSON می‌گیرند تا کلاینت بتواند همان را توست کند.
- **سکوت ممنوع:** انتخاب روش/موضوع نامعتبر، گزینهٔ خارج از محدوده، آزمون بدون نیت و… همه
  پیام می‌گیرند؛ هیچ ورودی‌ای بی‌واکنش رد نمی‌شود.

## مدل زبانی (هوش مصنوعی)

فال پایه قطعی و تکرارپذیر است (تضمین همان روز = همان نمادها)، ولی **خوانش نهایی** با
یک مدل زبانی و بر پایهٔ **نیت کاربر** نوشته می‌شود. لایهٔ مدل در `app/llm.py` است و سه اصل دارد:

1. **هیچ‌وقت کاربر را معطل نمی‌گذارد.** هر تماس سقف زمانی دارد (مسیر گشودن فال: ۶ ثانیه) و اگر
   همهٔ ارائه‌دهنده‌ها جواب ندهند، همان فال پایه و متن‌های آماده نشان داده می‌شوند. خرابی مدل هیچ
   صفحه‌ای را نمی‌شکند.
2. **ارائه‌دهندهٔ اصلی جمینای است و گروک پشتیبان.** به ترتیب امتحان می‌شوند؛ اگر کلید جمینای رد
   شود یا سرویس جواب ندهد، خودکار به گروک می‌رود. **مدارشکن** جلوی اتلاف وقت را می‌گیرد: ارائه‌دهنده‌ای
   که خطا داده، برای چند دقیقه رد می‌شود و این وضعیت حتی بعد از ری‌استارت سرور هم از لاگ دیتابیس
   یادآوری می‌شود (بدنبال آن، دور بعدی مستقیم به پشتیبان می‌رود).
3. **همه‌چیز ثبت می‌شود.** هر تلاش — موفق یا ناموفق — با ارائه‌دهنده، مدل، تأخیر، توکن‌های
   ورودی/خروجی، متن خطا و پیش‌نمایش پرامپت و پاسخ در جدول `llm_calls` می‌نشیند.

سه جای برنامه از مدل استفاده می‌کند:

| کاربرد | چه می‌دهد |
| --- | --- |
| خوانش نهایی فال | تیتر، یک پاراگراف شخصی دربارهٔ نیت، سه پیشنهاد عملی و یک جملهٔ دعوت |
| تفسیر تست شخصیت | توضیح می‌دهد چرا همین نتیجه از پاسخ‌های خودِ کاربر درآمده (با درصدهای واقعی) |
| پیام پاپ‌اپ امتیاز | یک متن کوتاه و متغیر که کاربر را به نوشتن پیشنهاد ترغیب می‌کند |

**فیلترشدن هم خطا حساب می‌شود، نه شکست.** هر دو سرویس پشت Cloudflare هستند و از بعضی
شبکه‌ها بی‌واسطه پاسخ نمی‌دهند (۴۰۳ با صفحهٔ HTML یا پیام «این منطقه پشتیبانی نمی‌شود»).
لایهٔ مدل این حالت را از «کلید خراب» جدا می‌کند:

- خطای فیلتر/منطقه → وضعیت `edge_blocked` یا `geo_blocked`، **پنجرهٔ کوتاه (۶۰ ثانیه)**؛
  یعنی همان لحظه که مسیر باز شود (پروکسی روشن شود) برنامه خودش، بدون ری‌استارت، به همان
  ارائه‌دهنده برمی‌گردد.
- خطای احراز هویت واقعی (`401`/`403` با پیام JSON سرویس) → پنجرهٔ بلند، چون تکرارکردنش فایده ندارد.

در تمام این مدت **سایت کامل کار می‌کند**: فال، تست‌ها، پنل و بقیهٔ بخش‌ها بدون مدل هم پاسخ
می‌دهند و کاربر فقط متن پایهٔ خود برنامه را می‌بیند. برای همین گفته می‌شود که دادهٔ «ماک»
از بیرون قابل تشخیص نیست: نبودِ مدل، هیچ صفحه‌ای را خالی یا خراب نمی‌کند.

**دستورهای سیستم** (System Prompts) در `app/prompts.py` و در یک دفتر مرکزی جمع شده‌اند: هم کد از
همان‌جا می‌خواند، هم پنل ادمین **فقط نمایش** می‌دهد (`مسیر مخفی/ai/prompts`). هیچ نسخهٔ دومی از
پرامپت‌ها در کد وجود ندارد، پس هرچه در پنل می‌بینی دقیقاً همان چیزی است که فرستاده می‌شود.

در پنل، صفحهٔ **هوش مصنوعی** (`مسیر مخفی/ai`) این‌ها را نشان می‌دهد: تعداد تماس‌ها، نرخ موفقیت،
میانگین و بیشترین تأخیر، توکن ورودی/خروجی، تعداد پاسخ‌های آمده از پشتیبان، تعداد درخواست‌هایی که
با مدارشکن رد شدند، مصرف ۱۴ روز گذشته، تفکیک مصرف به تفکیک کاربرد و مدل، فهرست تماس‌ها با
پیش‌نمایش پرامپت و پاسخ خام، فهرست ناموفق‌ها و خروجی CSV.

## تبلیغات (پنل)

از پنل، بخش **تبلیغات**، عکس یا ویدیوی چندثانیه‌ای را آپلود می‌کنی و همه‌چیز نمایشش را
خودت تعیین می‌کنی:

| تنظیم | یعنی چه |
| --- | --- |
| فایل | عکس (jpg/png/webp/gif/avif تا ۸ مگابایت) یا ویدیو (mp4/webm/ogv/mov تا ۳۲ مگابایت) |
| عنوان و متن کوتاه | چیزی که روی تبلیغ دیده می‌شود |
| لینک و متن دکمه | مقصد کلیک؛ خالی بگذاری، تبلیغ کلیک‌شدنی نیست |
| کجا نمایش داده شود | پاپ‌اپ روی همهٔ صفحه‌ها، بنر صفحهٔ خانه، یا هر دو |
| ردکردن | کاربر بتواند رد کند یا نه، و از ثانیهٔ چندم دکمهٔ ردکردن فعال شود |
| چند ثانیه بماند | زمان نمایش؛ برای ویدیو تا پایان خودِ ویدیو هم صبر می‌شود |
| بازهٔ ساعت | مثلاً فقط ۱۸ تا ۲۳ (بازهٔ شب‌رو هم می‌شود: ۲۲ تا ۲) |
| روزهای هفته | مثلاً فقط پنج‌شنبه و جمعه؛ هیچ روزی تیک نخورد = همهٔ روزها |
| بازهٔ تاریخ | از یک تاریخ جلالی تا تاریخ دیگر (خالی = همیشه) |
| سهمیهٔ روزانه | حداکثر چند بار به هر نفر در روز نشان داده شود (۰ = بی‌سقف) |
| «دیگر نشان نده» | اگر عدد بدهی، کاربر می‌تواند همان تبلیغ را چند روز نبیند |
| وزن | بین چند تبلیغ هم‌زمان، آن‌که وزن بیشتری دارد جلوتر است |

نکته‌های ریزِ طراحی:

- **حتی وقتی از پنل خاموش کنی، همان لحظه اثر می‌گذارد**؛ زمان‌بندی هم سمت سرور چک
  می‌شود، پس ساعت کاربر قابل دستکاری نیست.
- **هر نمایش/کلیک/ردکردن ثبت می‌شود** و در فهرست پنل، کنار هر تبلیغ، تعداد نمایش،
  کلیک، نرخ کلیک و ردکردن را می‌بینی. صفحهٔ **پیش‌نمایش** هر تبلیغ هم همان چیزی است که
  کاربر می‌بیند، به‌همراه نمودار روزانهٔ ۱۴ روز اخیر.
- **تبلیغ و پاپ‌اپ امتیاز با هم باز نمی‌شوند**: اگر پاپ‌اپ امتیاز باز باشد، تبلیغ حتی
  درخواست هم نمی‌شود (پس «نمایش» الکی ثبت نمی‌شود).
- **بدون تبلیغ، هیچ چیزی ساخته نمی‌شود**: اگر هیچ تبلیغی واجد شرط نباشد، صفحه فقط با
  یک درخواست کوچک (`/api/ad`) جواب "خالی" می‌گیرد و هیچ کدی اجرا نمی‌ماند.
- رسانه‌ها در `data/ads_media/` می‌نشینند (در `.gitignore`) و مسیر امن‌شان `/media/ads/…`
  است؛ نام فایل همیشه تازه ساخته می‌شود، پس نام فایل کاربر هیچ‌وقت روی دیسک نمی‌نشیند.
- خروجی CSV تبلیغات: `مسیر مخفی/export/ads.csv`

## امتیاز و نظر کاربران (پاپ‌اپ بازگشت)

اگر کاربر بیش از **۲۴ ساعت** غایب بوده باشد، در اولین صفحه‌ای که باز می‌کند یک پاپ‌اپ می‌بیند:

1. **مرحلهٔ اول: امتیاز ۱ تا ۵ ستاره.** با انتخاب ستاره، همان ستاره و ستاره‌های پایین‌ترش روشن می‌شوند.
2. **مرحلهٔ دوم: نظر آزاد.** متن ترغیبی با لحن صمیمی توضیح می‌دهد که نوشتهٔ کاربر مستقیم روی
   فال‌ها، تست‌ها و لحن برنامه اثر می‌گذارد و چند نمونهٔ پیشنهاد هم جلوی چشمش می‌گذارد.

جزئیات پیاده‌سازی:

- آخرین فعالیت کاربر در ستون `last_active_at` نگه داشته می‌شود (هر ۵ دقیقه حداکثر یک بار نوشته می‌شود
  تا هر درخواست دیتابیس را قفل نکند).
- به‌محض نمایش، `feedback_asked_at` ثبت می‌شود؛ پس یک رفرش، پاپ‌اپ را تکرار نمی‌کند و کاربر حداکثر
  یک بار در ۳۰ روز پرسیده می‌شود.
- پاپ‌اپ روی صفحه‌های ثبت‌نام، APIها، فایل‌های ثابت و پنل ادمین نشان داده نمی‌شود.
- فرم بدون جاوااسکریپت هم کار می‌کند (فرم سادهٔ HTML)؛ با جاوااسکریپت، ارسال پشت‌صحنه و پیام تشکر
  جایگزین می‌شود. متن ترغیبی هم بعد از باز شدن پاپ‌اپ و به‌صورت غیرمزاحم از مدل گرفته می‌شود.
- امتیاز و نظر در جدول `feedback` ذخیره و در پنل (`مسیر مخفی/feedback`) با میانگین، توزیع ستاره‌ها
  و خروجی CSV نمایش داده می‌شوند.

## آزمون‌ها

با سرور روشن، دو آزمون جداگانه در دسترس است:

```bash
python tools/smoke_test.py    # مسیر واقعی کاربر و پنل
python tools/edge_test.py     # ورودی‌های خراب و تهاجمی (۱۶۲ بررسی)
```

### آزمون لبه‌ها (`tools/edge_test.py`)

۱۹۶ ورودی خراب را می‌زند: شمارهٔ خالی و حرف‌دار، کد غلط،
نام کاربری تکراری و نامِ شبیه SQL و نامِ چند‌کیلوبایتی، تاریخ تولد ناممکن (۳۱ اسفند سال
غیرکبیسه، ماه ۱۳)، نیت ۲۰٬۰۰۰ کاراکتری، توکن فال قلابی، شناسهٔ تلاش دیگران، امتیاز صفر و شش،
کوکی جعلی، متد نادرست و بدنهٔ JSON خراب. هیچ‌کدام نباید ۵۰۰ بدهند.

سه چیز را به‌طور خاص می‌سنجد: **مسابقهٔ زمانی** (دو کاربر هم‌زمان یک نام کاربری ⇒ یکی موفق،
یکی پیام روشن، و در دیتابیس دقیقاً یک ردیف)، **توست‌ها** (پیام بعد از ریدایرکت می‌آید، با
رفرش تکرار نمی‌شود، خطای فرم توست می‌شود) و **ارقام فارسی** در ثبت‌نام.

تبلیغات هم زیر همین ذره‌بین است: فایل pdf/sh، فایل خالی، فایل غایب، عنوان خالی و
چندکیلوبایتی، لینک `javascript:` و `data:`، تاریخ ناممکن (۳۱ اسفند، ماه ۱۳، پایان قبل از
شروع)، ساعت و روز هفتهٔ نامعتبر، شناسه‌های قلابی و تلاش برای بیرون‌زدن از پوشهٔ رسانه.

هر اجرا شماره‌ها و نام‌های آزمون را تازه می‌سازد و در پایان همان‌ها را پاک می‌کند، پس
دیتابیس با اجراهای پیاپی شلوغ نمی‌شود.

### دودی‌تست

با سرور روشن، کل مسیر کاربر و پنل را یک‌بار چک کن:

```bash
python tools/smoke_test.py
```

۱۵۸ بررسی: ثبت‌نام با کد (ارقام لاتین و فارسی)، **انتخاب نام کاربری و رمز عبور** (ردشدن رمز کوتاه،
تکرار ناهمخوان، نام کاربری فارسی و نام کاربری تکراری)، **بسته‌بودن مسیر پیامکی برای شمارهٔ
ثبت‌نام‌شده** و «نمایش‌نشدن کد» برای حساب کامل، ورود با نام کاربری و رمز و ردشدن رمز اشتباه،
ثبت‌نام کامل روی یک کاربر تازه (نام و نام خانوادگی → تاریخ و ساعت تولد)، صفحهٔ «زندگی در عدد»،
ساخت فال، پاسخ‌دادن به تست، ورود مدیر، پروندهٔ کاربر و پروندهٔ کامل، **CRUD استخر فال** (ساخت،
ویرایش، حذف، پنهان، بازگرداندن)، خروجی‌های CSV و مسدودبودن دسترسی مهمان به پنل.

بررسی‌های تازهٔ این مرحله:

- **فال‌های نمادین:** هر هفت روش نماد بصری خودش را دارد و این الگوها یکتاست؛ تاروت سه کارتِ
  تکراری‌نشدنی با جایگاه و جهت، تاس سه تاس با نقطه‌های هم‌خوان با عدد، رون یک سنگ با گلیف.
- **امتیازدهی تست‌ها:** نتیجه از پاسخ‌های واقعی درمی‌آید، هر چهار محور MBTI درصد و قدرت ترجیح
  دارند، مجموع دو طرف هر محور همیشه ۱۰۰ است، درصد عامل‌ها از سقف حساب می‌شود و رتبهٔ فهرست
  نزولی است.
- **پاپ‌اپ امتیاز:** نمایش پس از ۲۴ ساعت غیبت، داشتن ستاره‌های ۱ تا ۵، لینک‌شدن فرم به
  `/feedback`، نشان‌داده‌نشدن دوباره در بازدید بعدی و ذخیره‌شدن امتیاز در دیتابیس.
- **پنل:** صفحهٔ مانیتورینگ هوش مصنوعی، فیلتر ناموفق‌ها، صفحهٔ دستورهای سیستم (بررسی می‌کند
  متن کامل هر سه سیستم‌پرامپت و قالب پیام کاربر واقعاً رندر شده) و صفحهٔ امتیاز و نظر.

کاربر آزمون تازه پیش از هر اجرا از پنل پاک می‌شود، پس اجرای مکرر دیتابیس را شلوغ نمی‌کند. کاربر
آزمون دوم (با نام کاربری `smoke_user`) اگر از نسخهٔ قبلی بدون رمز مانده باشد، در همان اجرا رمز می‌گذارد.

## مسیر کاربر (Journey)

1. **ثبت‌نام با شمارهٔ تلفن** — `/register` شمارهٔ موبایل ← `/verify` کد شش‌رقمی. کد در `/inbox`
   (شبیه‌سازی پیامک) و لاگ سرور دیده می‌شود. خانه‌های کد عمداً **چپ‌به‌راست** چیده شده‌اند و
   **ارقام فارسی** هم پذیرفته می‌شوند. این مسیر فقط برای شماره‌ای باز است که حساب کاملی ندارد.
2. **نام کاربری و رمز عبور** — `/signup`: بلافاصله بعد از تأیید کد. نام کاربری ۳ تا ۲۴ نویسهٔ
   انگلیسی (حرف، رقم، نقطه، زیرخط) و رمز حداقل ۸ نویسه. هش با **PBKDF2-SHA256 (۲۶۰٬۰۰۰ تکرار)**
   ذخیره می‌شود و خودِ رمز در دیتابیس نمی‌ماند.
3. **ورود** — `/login` با **نام کاربری + رمز عبور** (نه پیامک). پنج تلاش ناموفق، ورود همان حساب را
   ۱۵ دقیقه قفل می‌کند و همهٔ تلاش‌های ناموفق در جدول رویدادها ثبت می‌شوند.
4. **نام و نام خانوادگی** — `/welcome`: نام و **نام خانوادگی (اجباری)**، جنسیت (اختیاری)
5. **اطلاعات تولد** — `/birth`: تاریخ دقیق تولد هجری شمسی (روز/ماه/سال)، ساعت تولد و شهر.
   جدا از مرحلهٔ قبل است تا کاربر وسط ثبت‌نام رها نشود؛ با تاریخ تولد، پیش‌نمایش برج هم نشان داده می‌شود.
6. **زندگی در عدد** — `/life`: حدود **۳۰ کارت آماری** از تاریخ و ساعت تولد: سن دقیق تا روز،
   تعداد ضربان قلب، وعده‌های غذایی، هفته‌ها و روزهای عمر، نفس‌ها، پلک‌زدن‌ها، قدم‌ها، لیتر خون،
   ماه‌های کامل، جمعیت روز تولد (که چند نفر با او هم‌روز به دنیا آمده‌اند)، جمعیت کشور، سفر زمین
   به دور خورشید و... . با دکمهٔ اشتراک‌گذاری و لینک در پروفایل.
7. **روش و موضوع** — `/journey` هفت روش (حافظ، تاروت، طالع، عدد، رون، چینی، تاس) و ۹ موضوع
8. **نیت** — متن آزاد تا ۱۸۰ حرف
9. **صفحهٔ خوانش** — `/r/{token}` با انیمیشن گشوده می‌شود؛ ابیات، تعبیر، نمودار انرژی، اقلام شانس
10. **بعد از آن** — «فال تازه»، کپی متن، چاپ/PDF و «فال‌های من» در `/readings`
11. **تست‌ها** — `/tests` ده تست شخصیت (MBTI، پنج عامل بزرگ، خدایان یونانی، کهن‌الگوهای یونگ، انیاگرام، هفت چاکرا، زبان عشق، هوش‌های چندگانه، DISC، مزاج‌ها)

## حساب کاربر: شماره برای ثبت‌نام، رمز برای ورود

مشکل طراحی قدیم این بود که **تنها کلید ورود، شمارهٔ تلفن بود**؛ هر کسی که شمارهٔ کاربر را می‌دانست
می‌توانست درخواست کد کند و اگر کد را می‌دید (یا در نسخهٔ واقعی به خط او می‌رسید)، سر از حساب او درمی‌آورد.
الان قاعده این است:

- **شمارهٔ تلفن فقط برای ثبت‌نام است.** `users.phone` یکتاست؛ هر شماره فقط یک حساب دارد.
- **`/register` برای شماره‌ای که حسابش کامل شده، کد نمی‌فرستد** و با پیام «این شماره قبلاً ثبت‌نام
  کرده است» کاربر را به `/login` می‌فرستد. همین گارد در `/verify` هم هست (دفاع لایه‌ دوم).
- **`code_for_phone()` برای حساب کامل، کد را خالی برمی‌گرداند**؛ پس در `/verify` و `/inbox` هیچ کدی
  دیده نمی‌شود و کلید ورود روی صفحه لو نمی‌رود.
- **ورود بعدی فقط با نام کاربری + رمز** انجام می‌شود. نام کاربری یکتا و بدون حساسیت به بزرگی/کوچکی
  حروف است (`CREATE UNIQUE INDEX ... ON users(lower(username))`).
- **رمز با PBKDF2-SHA256 و نمک تصادفی** ذخیره می‌شود (قالب `pbkdf2_sha256$iterations$salt$hash`)
  و مقایسه با `hmac.compare_digest` انجام می‌شود. پنج تلاش ناموفق، ورود همان حساب را ۱۵ دقیقه قفل
  می‌کند و پیام خطا برای «نام کاربری ناموجود» و «رمز غلط» یکسان است تا وجود نام کاربری لو نرود.
- **کاربر بدون رمز** (کاربرانی که با نسخهٔ پیامکی قبلی ساخته شده‌اند) در اولین ورود به `/signup`
  هدایت می‌شوند و رمز می‌گذارند؛ بعد از آن مسیر پیامکی برای آن شماره بسته می‌شود.

> **باقی‌ماندهٔ پروتوتایپ:** چون پیامک واقعی ارسال نمی‌شود، کد ثبت‌نام برای شماره‌های *آزاد* روی صفحه
> دیده می‌شود؛ پس در این نسخه ممکن است کسی شمارهٔ دیگری را ثبت‌نام کند و آن را تصاحب کند. برای نسخهٔ
> واقعی `NESHANE_SHOW_OTP=0` را بگذار و پیامک واقعی وصل کن؛ آن‌وقت شماره فقط با کدِ رسیده به خط
> خودِ کاربر تأیید می‌شود. حساب‌هایی که ثبت‌نامشان کامل شده در هر حالت با پیامک باز نمی‌شوند.

## تصاویر فروشگاه (مارکت‌پلیس)

ده تصویر آمادهٔ بارگذاری در `marketing/screenshots/` هستند (۱۰۸۰×۱۹۲۰) و متن فروشگاه
(کوتاه/کامل/کلمات کلیدی) در `marketing/store-listing.md`.

آن‌ها طرح دستی نیستند: اسکریپت یک کاربر نمایشی می‌سازد، با نشست خودش چند خوانش و
یک تست کامل می‌سازد، HTML همان صفحه‌ها را از سرور زنده می‌گیرد و با کروم بی‌سر
اسکرین‌شات می‌گیرد؛ بعد هر اسکرین داخل ماکت گوشی و زیر تیتر تبلیغاتی می‌نشیند.

```bash
python -m uvicorn app.main:app --port 8020    # سرور بالا باشد
python tools/make_store_shots.py              # تصاویر را از نو می‌سازد
```

متن تیتر/زیرتیتر در `FRAME_COPY` داخل `tools/make_store_shots.py` است؛ پس با عوض‌کردن
یک عبارت و اجرای دوباره، تصاویر با متن تازه بازساخته می‌شوند. جزئیات در `marketing/README.md`.

## موتور فال چطور کار می‌کند؟

هر خوانش از یک **اثر انگشت** ساخته می‌شود:

```
sha256( نام | تاریخ تولد | ساعت تولد | شهر | موضوع | نیت | روش | تاریخ امروز | نمک )
```

از این هش یک مولد شبه‌تصادفیِ قابل‌تکرار ساخته می‌شود، بنابراین:

- **همان اطلاعات + همان روز = همان فال**
- **هر روز، فالت نو است** (چون تاریخ امروز بخشی از هش است)
- **«فال تازه»** با افزودن «نمک» جدید یک خوانش متفاوت می‌سازد

سپس موتور:

1. برج و عنصر را از تاریخ تولد محاسبه می‌کند
2. سیّارهٔ امروز را از روز هفته می‌گیرد و هم‌سویی‌اش را با سیّارهٔ تولد می‌سنجد
3. امتیاز پنج حوزهٔ انرژی را می‌سازد و وزن‌دهی می‌کند
4. کارت‌ها را از استخر محتوا برمی‌دارد و جمله‌های قالب‌دار را پر می‌کند
5. نمودار انرژی، اقلام شانس، کارهای امروز/امروز-نه و جملهٔ پایانی را می‌سازد
6. یک نسخهٔ متنی برای «کپی» آماده می‌کند

### افزودن محتوا

- **غزل/فال بیشتر:** `python tools/build_fortunes.py` (تعداد را با `WANTED` عوض کن)
- **کارت دست‌نویس:** یک دیکشنری با کلیدهای `id`, `verses`, `keywords`, `interpretation`, `guidance` به
  `HAFEZ_CARDS` در `app/content/hafez.py` اضافه کن
- **کارت تاروت:** کلیدهای `numeral`, `name`, `glyph`, `keywords`, `upright`, `reversed`, `advice`
- **مضمون تازه برای تعبیر:** یک تم به `THEMES` در `app/content/fortune_themes.py` اضافه کن

## ذخیره‌سازی

`app/db.py` روی **SQLite** کار می‌کند (`data/neshane.sqlite3`، حالت WAL) و این جدول‌ها را دارد:
`users`، `otp_codes`، `sessions`، `readings`، `journey_state`، `test_attempts`، `events`،
`admin_sessions`، `fortune_cards` (ویرایش و کارت‌های ساختهٔ مدیر)، `llm_calls` (لاگ هر تماس با مدل)
و `feedback` (امتیاز و نظر کاربران).

ستون‌های `family`، `username`، `password_hash`، `phone_verified_at`، `last_active_at`،
`feedback_asked_at`، `ai_note` و `ai_meta` و همچنین جدول‌های `llm_calls` و `feedback` با
**مهاجرت خودکار** به دیتابیس‌های قدیمی اضافه می‌شوند (ایندکس یکتای نام کاربری بعد از افزودن ستون
ساخته می‌شود)؛ لازم نیست کسی دستی کاری کند و دادهٔ کاربران از بین نمی‌رود.

برای اینکه فایل دیتابیس بی‌نهایت بزرگ نشود، در پنل و از صفحهٔ هوش مصنوعی می‌توانی ردیف‌های قدیمی
`llm_calls` را با یک دکمه پاک کنی (`db.purge_llm_calls`).

- لینک‌های `/r/{token}` و پروندهٔ کاربران با ری‌استارت پاک نمی‌شوند
- برای مهاجرت به Postgres/MySQL کافی است تابع‌های همین ماژول بازنویسی شوند؛ به موتور و قالب‌ها دست نمی‌زنیم

## UI / UX

- **مینیمال و آرام**: تایپوگرافی بزرگ، فضای سفید زیاد، گوشه‌های نرم، سایه‌های ملایم
- **RTL کامل** با ارقام فارسی در همه‌جا — جز **خانه‌های کد ورود** که عمداً چپ‌به‌راست‌اند
- **پوستهٔ روشنِ قفل‌شده** (`color-scheme: light only`): اپ عمداً همیشه روشن است. دلیلش یک باگ
  واقعی روی آیفون بود: مرورگر به تگ `<button>` رنگ را ارث نمی‌دهد و در **حالت تاریکِ سیستم**،
  رنگ متنِ پیش‌فرض دکمه‌ها سفید می‌شود؛ نتیجه این بود که متن گزینه‌های تست روی کارت سفید **نامرئی**
  می‌شد (بَج شماره و فلش دیده می‌شدند چون رنگ صریح داشتند، ولی متن نه). حالا هم `color-scheme`
  قفل شده، هم `button { color: inherit; -webkit-text-fill-color: inherit }` گذاشته شده و
  `.option__text` رنگ صریح خودش را دارد؛ پس متن گزینه‌ها در هر حالتی خوانا است.
- **احترام به `prefers-reduced-motion`** و یک لایهٔ اطمینان که هر عنصر نامرئی‌مانده را دستی نمایان می‌کند
- **انیمیشن‌های هدف‌دار**: نمایان‌شدن نوارها، شمارش عدد انرژی، برگشتن سه‌بعدی کارت، پردهٔ گشودن فال
- **دسترس‌پذیری**: کنتراست مناسب، فوکوس‌رینگ، `aria` روی نواحی مهم، امکان چاپ/PDF
- **موبایل‌فرست**: چیدمان‌ها در ۸۶۰ و ۶۴۰ پیکسل بازچینش می‌شوند
- **فونت**: اپ از فونت خودش استفاده می‌کند و پنل مدیریت از **وزیرمتن** (۵ وزن، بندل‌شده در
  `app/static/fonts/`، بدون هیچ CDN) — هر دو با `font-display: swap`
- **لندینگ**: هیرو با پیش‌نمایش زندهٔ همان موتور «زندگی در عدد»، شمارندهٔ آمار، کارت روش‌های فال
  و بخش‌های اعتماد/پرسش‌های پرتکرار
- **«زندگی در عدد»**: کارت‌های آماری با آیکون، عدد درشت و یک خط توضیح — هم در `/life` برای کاربر
  و هم داخل پروندهٔ پنل
- **نمادهای واقعی هر فال**: هر روش، شیء خودش را روی صفحه می‌گذارد تا با یک نگاه از بقیه جدا شود —
  تاروت سه کارتِ قاب‌دار (کارتِ وارونه واقعاً ۱۸۰ درجه می‌چرخد)، تاس سه مکعبِ ۵۴ پیکسلی با نقطه‌های
  درست، رون یک سنگِ سنگیِ گرد با گلیف، عدد یک لوحِ رنگی با رقم، و برج/حیوان نماد خودشان.
- **نتیجهٔ تست با فرمول خودش**: درصدها نسبت به سقفِ قابل‌کسب هر عامل حساب می‌شوند (پس همه‌چیز
  مصنوعی ۱۰۰٪ نمی‌شود)، کنار هر محور «قدرت ترجیح» می‌آید و کنار هر عامل برچسب «بالا/میانه/در حال رشد».
- **دسترس‌پذیری در پاپ‌اپ**: ستاره‌ها کنار ورودی رادیویی واقعی هستند (با کیبورد هم کار می‌کنند) و
  حالتِ روشن‌شدن ستاره‌ها با کلاس CSS می‌رود، نه با `:has()`، تا روی آیفون‌های قدیمی‌تر هم مطمئن باشد.
